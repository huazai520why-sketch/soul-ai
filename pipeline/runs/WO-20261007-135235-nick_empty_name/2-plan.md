# ② agent1 方案

## 根因
nick 表中 uid=499192198 与 uid=134486858 存在归一化后名称为空串的记录；空串作为 _row_sid 子串匹配条件时会匹配任意字符串，导致红点行在身份解析阶段被错误关联/污染，最终出现身份解析失败。因果链限定为：脏数据（空归一化名）→ 子串谓词恒真 → _row_sid 匹配集合被污染 → 红点行身份解析异常。

## 方案
在定界边界内，仅清理/修复 nick 表这两条归一化名称为空的记录，使其不再参与空串子串匹配；先备份再按 uid 精准删除或回填为非空安全占位值。优先采用备份后删除脏行（若该 nick 行确为异常空名），不修改任何代码、其他表或身份解析逻辑；执行前后用只读 SQL 验证，并观察 code_watch 日志与红点身份解析结果。

## 回滚
若删除后出现非预期影响，使用修改前生成的 soul_memory.db.bak_before_nick_empty_fix_时间戳 备份恢复数据库（停写后执行 .restore 或文件级还原），恢复后重新执行空串计数 SQL 确认回到修复前状态；如只影响单条，也可从事先 SELECT 出的完整行备份按原列值精确 INSERT 回 nick 表。本次不改代码、不重启服务，因此无代码回滚动作。

## 验收标准
- SELECT COUNT(*) FROM nick WHERE COALESCE(TRIM(normalized_name),'')='' 结果为 0，特别是 uid=499192198、134486858 无空归一化名记录。
- 针对 uid=499192198、134486858 的 nick 查询不再返回 normalized_name 为空串的行，且未误删其他 uid 或同 uid 的非空名称行。
- code_watch 日志中 nick_empty_name 相关告警在修复后不再新增，日志显示空名称检查通过/计数为 0。
- 红点行身份解析在修复后的新样本中不再因空串 _row_sid 子串匹配产生错误关联：解析结果中不再出现由空名导致的异常 uid 关联，可通过对应红点会话/消息的身份解析日志或结果表抽样核对。
- chatmsg、session 等边界外表数据在修复前后按 uid 抽样对比保持不变，证明修改仅限 nick 脏数据。

## 风险对照
1) 昵称归一化空串历史坑：不能把异常名简单归一化为 ''，也不能回填空串或纯空白；本方案直接删除空归一化脏行，禁止引入新的空占位。若业务要求保留行，占位值必须为非空、唯一且不会命中真实用户子串，但这超出最小修复，不建议在本次执行。2) 改码不重启不生效：本方案不改任何代码、不需要重启，避免规则/逻辑变更未生效问题；nick_empty_name.py 仅作为证据，不修改。3) 规则泛词误伤真人：删除条件严格限定 uid IN (499192198,134486858) 且归一化值为空，不按泛化关键词或昵称模糊匹配批量删除，防止误伤真人数据。4) 并行改文件互相覆盖：本方案无代码文件改动；SQL 操作前备份、按 uid 精准执行，禁止多人同时对 nick 表做写入或并行修复，执行期间应串行，避免互相覆盖或误删。5) 若实际归一化列名与 normalized_name 不一致，必须先通过表结构确认并替换，禁止猜测列名直接执行；DELETE 必须保留空串判定，避免删除同 uid 的有效昵称。
